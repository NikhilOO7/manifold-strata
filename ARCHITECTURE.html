Build a geometric knowledge field
over research papers.

A full-stack system that reads academic PDFs, extracts a typed knowledge graph with AI agents, and answers multi-hop questions in vector + graph space — spending the LLM only where it actually earns its cost. This document teaches the whole thing: the high-level architecture, the low-level mechanics, and exactly how you'd scale it from hundreds of nodes to millions.

00 · THE BIG IDEAReason in geometry, not in tokens

Most "chat with your papers" systems are an LLM call per hop: retrieve, ask the model, retrieve again, ask again. That's slow, non-deterministic, and expensive. The thesis of this project is different and worth internalizing before any code:

Build the graph with the LLM once; then answer questions by moving mass through the graph — not by calling the LLM per hop. Extraction needs language understanding, so we spend an LLM there. Resolution, ranking, multi-hop reasoning, and evidence selection are geometric operations (cosine similarity, Personalized PageRank, MMR) and cost zero LLM calls. The model is spent on one final, optional verbalization.

Recall, then refine

Extract liberally (high recall), then let cheap geometric passes — resolution, validation rules, PPR — sharpen precision. Cheap operations do the filtering.

Provenance is first-class

Every edge stores the exact sentence and section that produced it. Trust, evaluation, and repair all hang off this.

Deterministic where possible

A graph walk gives the same answer twice. The only stochastic step is the optional final sentence.

02 · HIGH-LEVEL DESIGNThe system at 10,000 feet

Four runtime concerns, one process (for now): a stateless API, a bounded background worker, the Postgres source of truth, and pluggable model providers. The dotted boundary is the single-process line — every dotted crossing is a seam you later replace to scale out.

Read this diagram as a list of seams. Browser↔API is HTTP (already horizontal). Worker is in-process today → BullMQ/Redis later. Event bus is an EventEmitter → Postgres LISTEN/NOTIFY later. Provider calls are behind one module → model router later. Nothing else changes.

03 · DATA MODELTwo tables are the graph

A property graph maps cleanly onto relational tables. nodes are vertices, edges are typed relations, sources is the provenance ledger, and the node_vectors/propositions tables are the geometric layer. Everything is stamped with a domain for multi-field isolation.

Why open text types, not enums

The extractor can discover a relation type we didn't predefine. Storing type as text means a new type needs no ALTER TYPE migration. Well-known types are a UI hint, not a DB constraint.

Why a propositions table

A 2000-char chunk is a poor retrieval unit. We split each accepted relationship's evidence into one atomic, embedded fact. Retrieval then composes small, precise units instead of re-stuffing giant chunks into a prompt.

04 · LLD — INGESTIONFrom an arXiv id to durable rows

Ingestion is long-running (minutes of model calls) so it must never block the HTTP request. The request enqueues and returns a job id immediately; a bounded worker drains the queue so we never hammer the model or starve the event loop.

// the queue is deliberately tiny — bounded concurrency over a durable job table
class JobQueue {
  private active = 0;
  private readonly pending: Task[] = [];
  enqueue(task) { this.pending.push(task); this.drain(); }
  private drain() {
    while (this.active < this.concurrency && this.pending.length)
      /* claim one, run it, decrement, re-drain */
  }
}
Crash recovery is a design requirement, not an afterthought. On startup the worker marks any job still in a non-terminal state as failed ("interrupted by restart, please retry") — because an in-process queue loses in-flight work on exit. The durable jobs table is what makes this recoverable.

05 · LLD — THE AGENT PIPELINEExtract → Resolve → Validate

Three responsibilities, deliberately separated. One mega-prompt that "does everything" is impossible to debug and impossible to evaluate. Splitting lets each stage have a single job, a single prompt, and a single failure mode — and lets us replace any stage with a cheaper non-LLM version.

① Extractor (LLM)

Reads a chunk + its section, emits entity mentions with spans and relationship triples with evidence text. Tuned for recall — it's fine to over-extract; later stages prune.

② Resolver

Maps "3DGS" / "3D-GS" → one canonical node. FIELD mode: embed every mention in one batch, match by max(cosine, name). Zero LLM calls per chunk.

③ Validator

Quality gate before insert. RULES mode checks temporal consistency (A can't extend a newer B) and type compatibility, and adjusts confidence — all deterministic.

The write step earns its own attention

A relationship extracted from three different chunks is the same claim, not three. Inserting three edges would triple its weight in the ranking step. So the write is an upsert: reinforce one edge's confidence (noisy-OR) and append a provenance row per occurrence.

// noisy-OR: repeated independent evidence raises confidence, bounded below 1
function combineConfidence(oldC, newC) {
  return Math.min(0.99, 1 - (1 - oldC) * (1 - newC));
}
// two 0.6 mentions → 0.84, three → ~0.94. Never reads as certain.

06 · LLD — THE KNOWLEDGE FIELDHow a question becomes an answer with ~1 LLM call

This is the heart of the system. Watch where the LLM is and isn't: a question is embedded, the closest nodes become seeds, Personalized PageRank spreads relevance across the graph, the highest-ranked nodes' propositions are gathered, MMR compresses them to a tight budget, and only then — optionally — one model call turns evidence into a sentence.

MMR: why not just take the top-k by cosine?

Pure top-k returns five sentences that all say the same thing. Maximal Marginal Relevance trades relevance against novelty: each pick must be relevant to the query and dissimilar to what's already chosen, under a character budget. You get diverse, non-redundant evidence — which both improves answers and shrinks the prompt.

// pick the item maximizing: λ·relevance − (1−λ)·max similarity-to-already-picked
score = λ * cosine(query, item) - (1-λ) * maxSimToSelected(item)

07 · INTUITIONPersonalized PageRank, watch it flow

Drop "ink" on the seed nodes (the ones nearest your query). Let it diffuse along edges — stronger edges carry more — while a fraction keeps teleporting back to the seeds so relevance stays local. Where the ink settles is your multi-hop relevance ranking. No language model is involved.

The scale fix. Textbook PPR power-iterates the whole graph ~30× per query — cost grows with the entire corpus even for a local question. We swapped in push-based local PPR (Andersen–Chung–Lang): mass is pushed outward from the seeds and the walk stops once residuals fall below a threshold. Work — and the result — is bounded by the seed neighborhood, so query latency stays flat as the graph grows from hundreds to tens of thousands of nodes.
// the whole bounded walk, in spirit
push(u):
  p[u] += α · r[u]                 // settle a fraction here
  mass  = (1−α) · r[u]; r[u] = 0   // the rest spreads
  for (v,w) in neighbors(u):
     r[v] += mass · w / degree(u)  // weighted by edge confidence
     if r[v]/degree(v) > ε: enqueue(v)  // only chase what still matters

08 · LLD — HYPERBOLIC LAYEREmbedding a hierarchy without distortion

A literature graph is a tree: methods extend methods extend foundational work. Euclidean space can't hold a tree — the number of descendants grows exponentially but the room around a point only grows polynomially, so siblings get crushed together. Hyperbolic (Poincaré-ball) space grows exponentially toward its boundary, so trees fit naturally: distance ≈ relatedness, and distance-from-center ≈ generality.

Why it's worth it. This unlocks queries plain embeddings can't answer: "what generalizes X?" / "what are the specializations of X?" — a capability a generic vector RAG simply does not have.

09 · LLD — ENTITY RESOLUTIONMaking "3DGS" and "3D Gaussian Splatting" one node

Deduplication is where naive knowledge graphs quietly rot — the same concept becomes five nodes and the graph fragments. We resolve geometrically: embed every mention once, and match against existing nodes by the max of exact-name and cosine similarity, scoped to the same domain so fields never cross-contaminate.

The trap we removed

A fuzzy includes() fallback once matched "GS" to half the graph. The fix: exact match first; the substring fallback fires only for long, unambiguous names. An ambiguous match returns nothing — a missing edge is recoverable, a wrong one silently corrupts.

The seam that scales

Resolution currently scans in-domain node vectors in JS. The marked pgvector swap point turns that scan into an ANN index lookup — same interface, different engine — when the corpus outgrows memory.

11 · PRODUCTION — OBSERVABILITY & SSEMake the claims measurable and the UI live

A "low-LLM" system has to prove it's low-LLM. Every query emits a structured trace line — latency, LLM calls, seeds, evidence, context size — the substrate for real OpenTelemetry spans later. And the old 2-second polling is replaced by a push bus.

12 · PRODUCTION — EVALUATIONNumbers, not vibes

The single most important thing separating a demo from an engineered AI system. A hand-curated gold set scores the pipeline in three layers, and reports cost alongside quality so you never improve one by silently wrecking the other.

LayerNeedsMetric
Extractionprovider onlyentity recall · relation precision / recall / F1 against gold passages
Resolutionprovider onlyalias-collapse accuracy + distractor rejection (does "NeRF" stay separate from "3DGS"?)
Retrieval + faithfulnesslive graphevidence hit-rate + LLM-judge entailment (is every claim in the answer supported by the evidence?)
This converts opinion into a regression gate. "FIELD mode is as good as LEGACY at a fraction of the cost" stops being a README sentence and becomes a number you can watch over time and block PRs on.

13 · PRODUCTION — AGENTIC REPAIRThe graph maintains itself

The validator checks edges at insertion; the world keeps changing. A repair agent re-audits the standing graph. Crucially, detection is free — pure graph/date logic flags suspects — and the LLM is spent only to judge each flagged edge against its own provenance.

Low confidence

Edges below a threshold are re-examined against their evidence.

Temporal impossibility

A paper "extending" a newer one — caught by comparing publication dates. Zero LLM calls to find.

Mutual contradiction

A and B each "extend" the other. The judge keeps the right direction, retracts the wrong.

Verdict is keep / adjust / retract, applied transactionally — and dry-run by default so you can inspect before mutating.

The discipline that makes this possible: every expensive thing sits behind a function with a stable signature. Scaling becomes "replace the body, keep the shape." That's the entire payoff of designing seams up front.

15 · DESIGN LESSONSWhat I'd tell someone building this from scratch

Spend the LLM where it's irreplaceable

Language understanding (extraction) needs it. Ranking, dedup, and selection are math. Conflating the two is how RAG bills get scary and answers get flaky.

Provenance or it didn't happen

Storing the evidence sentence per edge is what makes evaluation, faithfulness checks, and self-repair even possible. Add it on day one, not day one hundred.

Build the eval before the optimizations

You cannot tell if FIELD mode beats LEGACY without a scorecard. The harness is what licenses every later "improvement."

Design seams, not abstractions

Don't pre-build a plugin framework. Do put each expensive dependency behind one function so the future swap is local. Seams are cheap; premature abstraction is not.

Correctness bugs hide in the happy path

Duplicate edges, a no-op delete, a silent LIMIT dropping older nodes — none throw, all corrupt. The graph the whole thesis rests on must be guarded first.

Make it agent-shaped

Exposing the field over MCP reframes it from "an app" to "infrastructure other agents call." That's the 2026-native posture.
